# Infrastructure — Terraform (bastion + private app server)

Creates a private VPC where the app server is unreachable directly from
the internet. Two dedicated entry points exist instead: a bastion host
for SSH, and an Application Load Balancer for HTTP.

See `CICD_SETUP.md` in the repo root for the full setup guide and the
exact secrets needed (there are only two: AWS credentials). This file
covers infra-specific details only.

## What gets created

| Resource | Notes |
|---|---|
| VPC + 2 public + 2 private subnets | across 2 AZs |
| Internet Gateway + NAT Gateway | private subnet gets outbound internet (for `dnf`/`curl`), no inbound |
| Bastion (`t3.micro`, public subnet, Elastic IP) | the only SSH entry point |
| Application Load Balancer (public subnets) | the only HTTP entry point; forwards to the app server on port 80 |
| App server (`t3.micro` by default, **private** subnet, no public IP) | bootstrapped via `user_data` with Java 17, Tomcat 10.1, Nginx, DB schema pre-loaded, `/opt/deploy.sh` for future SSH-triggered deploys |
| RDS MySQL 8.0 (`db.t3.micro`) | private subnets only, security group only allows 3306 from the app server, password generated by `random_password.db` |
| SSH key pair | generated by Terraform (`tls_private_key`), public half installed on both the bastion and app server, private half stored only in SSM Parameter Store |

Change instance sizes, region, or CIDR ranges in `terraform/variables.tf`.

## Security notes

- The app server has **no public IP** — `aws_instance.app` has no
  `associate_public_ip_address` and sits in a private subnet. It can only
  be reached via the ALB (HTTP, port 80 only) or the bastion (SSH, port
  22 only) — both enforced at the security-group level, not just by
  routing.
- RDS is **never** publicly accessible — same pattern, private subnets,
  security group only trusts the app tier.
- The SSH private key is never a GitHub secret, never committed, and
  never written to disk outside of the few seconds a deploy job holds it
  in a temp file on the runner (cleaned up in the workflow's last step
  even if the job fails).
- The DB password is generated by Terraform and never appears in this
  repo, in GitHub, or in any log.
- `terraform.tfvars` and `*.tfstate` are git-ignored regardless, as a
  second line of defense.

## Running it locally instead (optional)

```bash
cd terraform
terraform init \
  -backend-config="bucket=tfstate-skillexchange-<your-account-id>" \
  -backend-config="key=skillexchange/terraform.tfstate" \
  -backend-config="region=us-east-1"
terraform plan
terraform apply
```
(The bucket must already exist for a local run — the GitHub workflow
creates it automatically on its first run; locally, create it yourself
first with `aws s3api create-bucket --bucket tfstate-skillexchange-<your-account-id>`.)

## Tearing it down

```bash
cd terraform
terraform destroy
```
